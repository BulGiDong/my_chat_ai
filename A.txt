현재 말투 테스트 시스템을 한 단계 더 안정화해라.

현재 결과:

* 테스트 케이스 30개
* 수정 전 통과율 93.3%
* 수정 후 통과율 96.7%
* 실패 1건: 운동 관련 답변에 "화이팅"이 포함됨
* 생성된 파일:

  * tone_test_cases.json
  * scripts/run-tone-tests.mjs
  * tone_test_report.md
  * tone_prompt.md

목표:
특정 실패 1건만 하드코딩해서 막지 말고, 실제 앱과 테스트가 같은 프롬프트를 사용하도록 정리하고 반복 테스트를 통해 말투 안정성을 검증해라.

중요:

* 앱 UI 수정 금지
* 이모티콘 기능 수정 금지
* 답장 지연 기능 수정 금지
* 선톡 기능 수정 금지
* OpenAI 호출 구조 수정 금지
* 특정 입력에 대한 고정 답변 추가 금지
* fallback 추가 금지
* 기존에 잘 통과한 말투를 무너뜨리지 말 것

## 1. 실제 프롬프트 연결 상태 확인

먼저 아래를 확인해라.

* `/api/chat`이 실제로 어떤 프롬프트 파일을 import하는지
* `tone_prompt.md`가 실제 API 요청에 사용되는지
* `lib/prompts/style.ts`가 실제 API 요청에 사용되는지

테스트와 실제 앱이 서로 다른 프롬프트를 사용하고 있다면 수정해야 한다.

권장 방향:

* 말투 원본은 `tone_prompt.md` 하나로 관리
* `/api/chat`이 서버에서 `tone_prompt.md`를 읽어 system prompt로 사용
* 테스트 스크립트도 같은 `/api/chat`을 호출하므로 실제 앱과 정확히 같은 프롬프트가 검증되게 한다

단, 현재 구조상 `lib/prompts/style.ts` 유지가 더 안전하면:

* `tone_prompt.md`와 `style.ts`가 서로 다른 내용을 갖지 않게 통합
* 최종적으로 프롬프트 원본은 한 곳만 존재하게 정리

프롬프트 경로를 바꾸기 전에 현재 import 관계를 먼저 조사하고, 최소 수정으로 처리해라.

## 2. "화이팅" 실패를 과적합 없이 수정

"화이팅"을 모든 상황에서 무조건 금지하지 마라.

하윤호의 실제 말투에서 거의 사용하지 않는 표현이라면 아래 원칙을 프롬프트에 추가해라.

* 공부, 운동, 힘든 상황에서 정형적인 응원 문구보다 짧고 따뜻한 반응을 우선한다
* "화이팅", "힘내", "응원할게" 같은 전형적인 응원 문구는 낮은 빈도로만 사용한다
* 대신 실제 말투에 가까운 표현을 사용한다

선호 예시:

* 아이구 고생하넹
* 헐 힘들겟당 ㅠ
* 오 열심히 하네 ㅎ
* 조시미 해
* 너무 무리하진마 ㅠ
* 운동 열심히 하넹

피할 예시:

* 화이팅!
* 운동 화이팅!
* 힘내!
* 응원할게!
* 끝까지 최선을 다해!

중요:
단순히 코드에서 "화이팅" 문자열을 삭제하거나 다른 고정 문장으로 치환하지 마라.
프롬프트의 전반적인 응원 말투 예시를 실제 말투 중심으로 보정해라.

## 3. 테스트 케이스 확대

`tone_test_cases.json`을 30개에서 최소 80개로 확대해라.

분포:

* 평범한 대화 12개
* 질문에 대한 답변 10개
* 공부 8개
* 운동 8개
* 음식/배고픔 8개
* 힘듦/슬픔/화남 10개
* 보고싶음/애정 표현 8개
* 장난/놀림/과장 10개
* 정보 질문 6개

기존 30개는 유지하고 새로운 케이스를 추가해라.

운동 테스트 예시:

* 나 운동중
* 오늘 하체함
* 운동 너무 힘들어
* 이제 마지막 세트
* 헬스장 왓오
* 유산소중
* 운동 끝낫다
* 오늘 운동 갈까말까

운동 답변 기대 특징:

* 짧고 따뜻함
* 전형적인 응원 구호보다 반응형 말투
* 질문을 억지로 붙이지 않음
* 같은 표현만 반복하지 않음

## 4. 반복 실행으로 안정성 검사

모델 응답은 매번 달라질 수 있으므로 각 테스트를 한 번만 실행하지 마라.

`scripts/run-tone-tests.mjs`를 수정해서:

* 각 입력을 기본 3회씩 실행
* 테스트용 환경변수로 반복 횟수를 바꿀 수 있게 구현

예:
`TONE_TEST_RUNS=3`

각 케이스는 3번 중 하나라도 실패하면 아래를 따로 기록:

* 완전 통과
* 불안정 통과
* 반복 실패

보고서 통계:

* 총 API 호출 수
* 케이스 기준 완전 통과율
* 응답 기준 전체 통과율
* 한 번 이상 실패한 불안정 케이스 수
* 반복 실패 케이스 수

## 5. 자동 검사 개선

기존 검사를 유지:

* 3문장 이상
* 일반 대화 30자 초과
* 질문 2개 이상
* 설명형 말투
* 상담사 표현
* forbiddenPatterns
* "니가/니는/니꺼"

추가 검사:

* 정형적 응원 표현 남발

  * 화이팅
  * 힘내
  * 응원할게
  * 잘할 수 있어
  * 넌 할 수 있어
* GPT식 대화 연장 표현

  * 뭐 도와줄까
  * 더 이야기해볼래
  * 궁금한 거 있으면
  * 뭐 물어볼래
* 같은 테스트의 3개 응답이 모두 완전히 동일한지
* 지나치게 차가운 단답인지

  * 오
  * 헐
  * 웅
  * 엥
    단독 답변은 문맥에 따라 수동 검토 대상으로 표시

주의:
문자열이 포함됐다고 무조건 전부 실패시키지 말고, 테스트별 forbiddenPatterns와 문맥을 우선해라.
예를 들어 사용자가 직접 "화이팅이 무슨 뜻이야?"라고 물은 정보 질문은 실패로 처리하면 안 된다.

## 6. 수정 전후 비교 절차

순서를 반드시 지켜라.

1. 현재 프롬프트로 80개 × 3회 기준선 테스트
2. `tone_test_report_before_v2.md` 저장
3. 반복되는 실패 유형 분석
4. 프롬프트 최소 수정
5. 동일한 80개 × 3회 재실행
6. `tone_test_report_after_v2.md` 저장
7. 전후 비교 보고서 `tone_test_comparison_v2.md` 생성

비교 보고서:

* 수정 전 완전 통과율
* 수정 후 완전 통과율
* 응답 기준 통과율
* 불안정 케이스 변화
* 개선된 유형
* 새로 악화된 유형
* 여전히 사람이 검토해야 하는 답변
* 대표 개선 사례 5개
* 대표 실패 사례 5개

## 7. 프롬프트 수정 원칙

* 실패한 한 문장에 맞춘 하드코딩 금지
* 규칙을 계속 길게 추가하지 말 것
* 중복된 규칙은 줄일 것
* 실제 말투 예시를 우선할 것
* 현재 잘 작동하는 장난, 애칭, 정보 설명 말투는 유지할 것
* 프롬프트 수정량은 최소화할 것
* 수정 전 프롬프트 백업 파일을 남길 것

추천 백업:

* `tone_prompt_before_v2.md`
